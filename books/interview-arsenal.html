READ THE ROOM

How Terraform Interviews Work

🧠 P4 · DECODER

Terraform interviews test three things in order: can you define it, can you explain the mechanism, and can you survive the disaster. Most candidates stop at rung one — this book rungs every question three high.

📋 The shape of the interrogationRound 1 screens definitions (what is state, what does init do). Round 2 probes mechanisms (why a saved plan, what a lock protects). Round 3 replays disasters (dead CI holder, deleted state, -/+ on a database). Safe answers pass rounds 1–2; only senior depth closes round 3.

1The 3-rung decoder

RungWhat it isWhat the interviewer hears
✅ SafeCorrect definition, 2 lines“Knows the tool — ask me harder.”
🚀 Senior depthMechanism + WHY“Has run this in prod — topic closed.”
🚩 Red flagConfident wrong-signal answer“Dangerous near prod — probe deeper.”
🎯 How to climbOpen safe on every question. If the interviewer leans in, spend the senior rung. Never volunteer a red-flag-shaped sentence — each question below names yours so you can avoid it.

2The 4 interviewer archetypes

  • 📖 The Definitionalist — “Define state.” Wants crisp sentences. Feed rung 1, stop. Rambling mechanisms here reads as bluffing.
  • ⚙️ The Mechanic — “What happens when two applies collide?” Wants the mechanism (locks, bindings, plan files). This is rung 2 territory.
  • 🔥 The Arsonist — “State deleted, prod passionate, go.” Wants calm triage order: inspect, never assume, next plan heals. Never promise rollback.
  • 🔍 The Auditor — “How does your team gate applies?” Wants PR plan-gate-apply, fmt -check, pinned providers, no committed secrets. Process answers only.
🚩 Universal red flags“We apply with -auto-approve by hand.” “State is in git so everyone has it.” “Force-unlock first, ask later.” Any one of these can end an interview on its own.

CALIBRATION

The 30-Second Answers

⏱ P5 · 6 SCRIPTS

Six answers you must deliver cold, in 30 seconds each. Say the Say line verbatim; the Lands line is why it works.

①What is Terraform?
Say: “Terraform is HashiCorp's tool for building, changing, and versioning infrastructure — I declare end-state in HCL, it figures out the API calls. Single Go binary, 2014, one workflow across clouds.”
②Why not ClickOps?
Say: “Console infra is tribal knowledge — nobody can answer what prod is or who changed it Tuesday. In Terraform, git log answers both, and every change passes plan review first.”
③State in one breath?
Say: “State is Terraform's memory: a JSON map of config to real IDs, IPs, and dependencies. Config says what I want, state says what exists, refresh verifies — delete it and Terraform forgets everything.”
④Plan before apply?
Say: “Plan previews, apply executes — and apply on a saved plan file runs exactly what was reviewed, no drift window. Bare apply in prod is how outages happen.”
⑤Modules?
Say: “Modules package infra like functions — inputs vary per caller, outputs cross the boundary as plain values like module.vpc.vpc_id. Registry modules get version pins, or upstream edits you at 3 AM.”
⑥Floci?
Say: “Floci is a local AWS emulator — container on port 4566, dummy creds plus endpoint override. I ran init → plan → apply → destroy against it and proved idempotence with a clean second plan.”
✓ Rehearsal ruleRecord yourself. Any answer over 30 seconds is a rung-1 answer with rung-2 fat on it — trim, don't add.

ZONE 1 · FUNDAMENTALS

What Terraform Is & Why It Exists

🟢 Z1 · 6Q
Q1 🔥?Terraform in one sentence — what is it?
✅ Safe (junior→mid)A tool for building, changing, and versioning infrastructure — declare what you want in config, Terraform makes reality match.
🚀 Senior depthHashiCorp, 2014, single Go binary with zero runtime. Manages existing providers (AWS, Cloudflare…) and custom in-house ones against any API — breadth is the whole point.
🚩 Red flag“Config manager / AWS-only / container orchestrator” — that's Ansible, CloudFormation, K8s. Naming the wrong layer fails round 1 instantly.
Q2 🔥?Declarative vs imperative — which pair is correct?
✅ Safe (junior→mid)Declarative states WHAT (Terraform); imperative scripts HOW (playbooks).
🚀 Senior depthTerraform takes end-state and derives ordering plus API calls itself — you never write the steps. Playbooks list steps to execute, with no state to diff against.
🚩 Red flagThe inverted pair (Terraform=HOW). It's the exam's favorite trap shape — interviewers use it the same way.
Q3 🔥?Same config applied twice — second plan shows…? Why?
✅ Safe (junior→mid)0 to add, 0 to change, 0 to destroy — “No changes.” Healthy steady state.
🚀 Senior depthIdempotence: same code → same infra, re-apply is a no-op by design. Refresh re-read reality, compare found zero drift: desired == known == real.
🚩 Red flag“Terraform skips planning” — it planned fully, then did nothing. And “faster on repeat” confuses caching with idempotence.
Q4?AWS + Cloudflare + GitHub in one apply — why Terraform?
✅ Safe (junior→mid)Platform-agnostic: one apply across any providers the moment a second API enters.
🚀 Senior depthCloudFormation can't leave AWS; splitting tools loses the single plan. Speed, community, practices are all true of Terraform and all miss the question — scope is the answer.
🚩 Red flagAnswering “it's faster” or “great community” — true, irrelevant, and it tells a Mechanic you dodge scope questions.
Q5?“Configure Nginx and users on 200 existing servers.” Best fit?
✅ Safe (junior→mid)Ansible — that's OS-level config of long-lived hosts, the config-management layer.
🚀 Senior depthTerraform provisions; it doesn't babysit fleets. Existing hosts + packages/users → Ansible. New infra + lifecycle → Terraform. Golden images → Packer.
🚩 Red flag“Terraform with a provider per package manager” — absurd layering. CloudFormation is doubly wrong: wrong layer AND single cloud.
Q6?AWS-only shop, deepest AWS integration wanted?
✅ Safe (junior→mid)CloudFormation — native depth is its entire value proposition.
🚀 Senior depthPrice depth vs breadth out loud: free, native, StackSets, auto-rollback — at the price of every other cloud. Knowing when NOT to pick Terraform is a senior signal.
🚩 Red flag“Terraform everywhere regardless” — breadth is not depth, and the stem priced depth.

ZONE 2 · STATE & BACKENDS

Memory, Locks & Ledger Surgery

🟡 Z2 · 8Q
Q1 🔥?What does terraform.tfstate actually store?
✅ Safe (junior→mid)JSON memory mapping config to real objects: IDs, IPs, ARNs, CIDRs, dependency edges — what the APIs returned after apply.
🚀 Senior depthFour functions: track (what's mine), compare (desired vs actual → plan diff), metadata (values config never declared), perform (cache so plan skips re-querying).
🚩 Red flag“Re-queried live every second, state optional” or hand-editing the JSON — every fix has a state command; hand edits corrupt.
Q2 🔥?Five engineers, one local state file — first fix?
✅ Safe (junior→mid)Remote backend. Local + two writers = last apply wins silently, then duplicates.
🚀 Senior depthS3 + DynamoDB, two jobs: versioned encrypted bucket stores, lock table guards. Backend checklist is all three — versioning + encryption + locking; one pillar is a half answer.
🚩 Red flagCommitting tfstate to git or emailing it around — state holds secrets in plaintext plus the keys to everything.
Q3?Sensitive values in state — how do you handle them?
✅ Safe (junior→mid)They sit in state — so state never enters git, backend is encrypted, access is restricted.
🚀 Senior depthLeak paths multiply: tfvars values, CI logs echoing outputs raw. Encrypt the backend, mark variables sensitive, keep secrets out of logs and repos.
🚩 Red flag“Base64 is encryption” thinking, or terraform output -raw secrets into CI logs.
Q4 🔥?Second apply starts while the first holds the lock?
✅ Safe (junior→mid)It waits or fails with a lock error — coordinate, queue, serialize. A live lock means a live writer.
🚀 Senior depthForce under a LIVE holder corrupts state for both runners — the cardinal sin. Force is for the dead only; per-env lock tables isolate blast radius.
🚩 Red flag“Force-unlock first, ask later.” Uttering this near a live apply ends interviews.
Q5?Lock held by a dead CI runner — recover?
✅ Safe (junior→mid)Confirm death (job red, no live process), then force-unlock by ID. Two steps, in order.
🚀 Senior depthLocks are protective, not punitive. Deleting the table destroys locking for everyone; restoring backups fixes state, and the lock isn't state.
🚩 Red flagDeleting the lock table, or waiting forever on a dead process.
Q6?Rename web → app with zero rebuild?
✅ Safe (junior→mid)terraform state mv — the binding moves, the cloud object never notices, next plan is empty.
🚀 Senior depthThree verbs, three fates: mv renames, taint schedules destruction, rm forgets. Snapshot raw state (state pull) before any surgery, plan-verify after.
🚩 Red flagTaint/recreate for a rename (downtime), or rm + re-apply (plans a delete+create pair).
Q7?state rm vs destroy?
✅ Safe (junior→mid)rm forgets — object lives and keeps billing. Destroy deletes — object dies.
🚀 Senior depthrm means “keep it, unmanaged” — say so in the commit message, or the next engineer finds an orphan burning money. Destroy first when you mean destroy.
🚩 Red flagUsing rm as “cleanup.” It feels like cleanup; it's abandonment.
Q8?Adopt hand-built VPC vpc-0ab1 under management?
✅ Safe (junior→mid)Write the resource block first, import to bind the ID, plan until the diff is empty. Import binds identity only — never generates config.
🚀 Senior depthMatch config to reality before importing or the first plan shows a diff. Inverse lesson: delete state and Terraform forgets everything — next apply births duplicates.
🚩 Red flagHand-editing state JSON to “adopt” — or import with no block and hoping.

ZONE 3 · WORKFLOW & CLI

The Loop: init → plan → apply

🟡 Z3 · 6Q
Q1 🔥?Fresh clone on a new laptop — first command, and what appears?
✅ Safe (junior→mid)terraform init — downloads provider binaries, installs modules, configures the backend. Nothing works until it runs.
🚀 Senior depthBinaries land in .terraform/ (ignored, re-fetchable); the lock file pins EXACT builds (committed). Bumping a constraint does nothing until init -upgrade — plan keeps the locked binary.
🚩 Red flagPlanning before init, or committing .terraform/ — megabytes of regret for zero reproducibility.
Q2 🔥?Core workflow in order?
✅ Safe (junior→mid)Write → init → plan → apply. First word is write — init needs something to install for.
🚀 Senior depthPlan is read-only and safe anytime — run it on every PR. Read the diff symbols: + add, ~ change, - destroy. A -/+ on a database means stop and snapshot.
🚩 Red flag“Plan is optional, apply covers it” — apply-without-plan is the anti-pattern in prod.
Q3?Why apply a saved plan file instead of bare apply?
✅ Safe (junior→mid)apply tfplan executes EXACTLY the reviewed diff — what you saw is what runs, no drift window.
🚀 Senior depthPR → plan posted → merge → gated apply: infra gets code-review discipline. -out serializes any plan, including destroy previews (plan -destroy -out).
🚩 Red flagAuto-apply on merge skipping human review — the pipeline judges what nobody read.
Q4?Apply interrupted halfway (Ctrl+C) — what is true?
✅ Safe (junior→mid)Partial stands — finished creates stay, state is written incrementally. Next plan reconciles. Never promise rollback.
🚀 Senior depthFailed apply guarantees nothing about the world: inspect state AND reality, then let the next plan heal. Hand-typed -auto-approve in prod is how the interruption finds you.
🚩 Red flag“All-or-nothing rollback” or “retry resumes where it stopped” — both fictions; re-entry is a fresh plan.
Q5?fmt vs validate in CI — which gate does what?
✅ Safe (junior→mid)fmt -check fails the build on unformatted HCL with zero writes (bare fmt is the local fixer). Validate checks syntax with zero cloud contact.
🚀 Senior depthGate order from a verified pipeline: fmt -check → init → validate → apply → verify live → idempotent re-plan. -recursive covers subfolders, -diff previews without writing.
🚩 Red flagRewriting in CI (gates must not mutate) or “validate needs credentials” — it needs neither network nor keys.
Q6?Test a format() expression without applying?
✅ Safe (junior→mid)Pipe it to console — evaluates with zero project context, touches nothing.
🚀 Senior depthConsole reads installed providers (needs init). For drift, modern form is plan -refresh-only — explicit read-only sync; bare refresh is legacy.
🚩 Red flag-target apply “just to test” — real changes for a syntax check. Writing a .tf for a one-liner is pure toil.

ZONE 4 · VARIABLES & CONFIG

Inputs, Precedence & Types

🟡 Z4 · 6Q
Q1 🔥?Defaults, TF_VAR, terraform.tfvars, -var all set — who wins?
✅ Safe (junior→mid)-var wins. Ladder top-down: CLI flags → files → env vars → defaults. Value surprise? Strip top-down; the stray flag is the prime suspect.
🚀 Senior depthEnv sits BELOW files, not above — the classic inversion. Per-team sizes come from variables with per-caller values, never from copied repos or console edits.
🚩 Red flag“Env beats files” or “defaults override” — reciting the ladder backwards fails the easiest senior probe there is.
Q2?terraform.tfvars vs *.auto.tfvars — the difference?
✅ Safe (junior→mid)terraform.tfvars is the single auto-loaded values file; *.auto.tfvars are layered overlays loaded lexically in name order.
🚀 Senior depthExplicit -var-file vs automatic layering: overlays stack (base.auto.tfvars → prod.auto.tfvars), so later names win. One file can't layer; overlays can't be explicit.
🚩 Red flagSecrets in either file committed to git — layering doesn't launder credentials.
Q3?What gets committed: real tfvars or the example?
✅ Safe (junior→mid)Template shared, secrets local: commit *.tfvars.example, ignore real *.tfvars.
🚀 Senior depthFull gitignore canon: ignore .terraform/, tfstate (+backup), real tfvars. Commit lock file + versions.tf — reproducibility is the half interviewers grade.
🚩 Red flag“Commit tfvars so the team stays in sync” — sync via the example, never via values.
Q4?TF_VAR_tags for a map variable — exact syntax?
✅ Safe (junior→mid)Single-quoted HCL: TF_VAR_tags='{Env="prod"}' — shell-safe quoting so braces survive.
🚀 Senior depthSame rule for objects. Bare braces split on spaces, double quotes interpolate — both corrupt before Terraform ever sees the value.
🚩 Red flagUnquoted complex TF_VAR and “Terraform parsed it wrong” — the shell ate it, not Terraform.
Q5?TF_VAR_count="three" on a number var — result? And for_each over a bare list?
✅ Safe (junior→mid)Type error at plan — fail fast, no silent ignore, no auto-correction. Bare lists fail for_each too — wrap with toset().
🚀 Senior depthSets over lists because keys are identity: stable, unique, rename-proof. Indices shift on middle removal (the count trap), duplicates collide, renames rebirth.
🚩 Red flagCount-indexing named instances, or “strings coerce quietly” — the type system fails loudly on purpose.
Q6?When do validation blocks run — and a required var with nothing provided?
✅ Safe (junior→mid)At plan: reject bad input with your message before any API call, before any cost. Missing required value → plan prompts (dies under -input=false in CI).
🚀 Senior depthFail-fast everywhere: conditions with contains() gate env names at plan, not at the invoice. Unprovided required vars break non-interactive pipelines — always provide or default.
🚩 Red flag“Validation runs after apply” or comments-as-validation — comments describe, they enforce nothing.

ZONE 5 · RESOURCES & LOGIC

Count, for_each & Providers

🔁 6 Q · IDENTITY IS EVERYTHING
📋 The one lessonUnder count, the index is the identity — remove the middle and everything after shifts. Under for_each, the key is the identity — edits touch one instance only. Say that sentence and half this zone answers itself.
Q1 🔥count vs for_each — when do you use which?
✅ Safe (junior→mid)count clones N identical copies addressed web[0], web[1]; for_each stamps one instance per key, addressed web["blue"]. Copies → count; named things → for_each.
🚀 Senior depthIndex identity vs key identity: deleting web[1] under count renames web[2]→web[1] and rebirths the tail; under for_each only that key is destroyed. Only keys survive reordering — that is why sets/maps, never lists, feed for_each.
🚩 Red flag"They're interchangeable" — signals you've never removed an item from the middle of a counted fleet and watched the cascade in the plan.
Q2 🔥for_each over a bare list fails. Fix?
✅ Safe (junior→mid)for_each needs a set or map. Wrap it — for_each = toset(var.list) — or build a key map. Lists re-index, so they can't supply stable identity.
🚀 Senior depthtoset() casts list → stable set so each value becomes its own key; for richer objects, a map gives you each.key / each.value with per-field types. Duplicates collide at plan time — that error is the identity check working.
🚩 Red flag"Just use count instead, always" — dodges the identity problem instead of solving it; the next edit rebirths the fleet.
Q3count = 3 → count = 2. What gets destroyed?
✅ Safe (junior→mid)web[2] — the tail. Count removes from the end; web[0] and web[1] are untouched.
🚀 Senior depthThe corollary is the real interview answer: removing from the middle (targeted destroy of web[1]) shifts every later index and rebirths the tail. for_each keys don't shift — the exam's core repetition lesson, and the reason fleets use keys.
🚩 Red flag"web[0]" or "all three" — guessing reveals you've never read a count-shrink plan line by line.
Q4How do you make a resource conditional, and read it safely?
✅ Safe (junior→mid)count = var.on ? 1 : 0 toggles one instance; read it with one(x[*].attr) — null when off. Never index x[0] directly: it explodes when the resource is absent.
🚀 Senior depthSplat always yields a list (empty when off), so one() collapses 1→value / 0→null deterministically. Outputs over the toggle stay clean — null when off, no conditional wiring downstream.
🚩 Red flag"x[0] with a try() around it" — try() is for optional nested access, not for papering over an addressing choice the language already solved.
Q5dynamic blocks, splat, count — which layer does each work at?
✅ Safe (junior→mid)Nested repetition → dynamic (N ingress stanzas from one variable, zero HCL edits per rule). Whole-resource clones → count/for_each. Reading across instances → splat (aws_instance.web[*].public_ip) or a for-map for name→IP.
🚀 Senior depthWrong layer is the classic bug: count on the security-group resource clones whole SGs when you wanted rules; hardcoding rules can't vary per caller. Check the layer first — nested block → dynamic, every time.
🚩 Red flag"Splat generates blocks" — splat reads collections; it never generates anything. Confusing read vs generate fails the layer question.
Q6 🔥Two regions, one apply — plus how providers version safely?
✅ Safe (junior→mid)Second provider "aws" { alias = "eu" } block; opt in per resource with provider = aws.eu. Pin in required_providers (~> 5.0); commit .terraform.lock.hcl so every machine downloads identical bits.
🚀 Senior depthCore plans, providers execute — plugins over RPC, and anyone can write one against any API. Forgetting the alias lands both VPCs in one region (peering dies on overlap); bumping a constraint does nothing until init -upgrade rewrites the lock. Never put static credentials in the block — env vars only.
🚩 Red flag"A second Terraform install" or credentials pasted in the provider block — one invents machinery, the other commits the incident.

ZONE 6 · MODULES

Consume, Author, Version

📦 6 Q · CONTRACT: SOURCE + IN + OUT
📋 The contractEvery module call is three parts: source (where the code lives), inputs (what you feed it), outputs (what it hands back). A fourth invented part — credentials inside, state inside — always marks the distractor.
Q1 🔥How does a stack consume module outputs?
✅ Safe (junior→mid)As a normal reference — module.vpc.private_subnets[0] is a value like any other. Root calls children; children expose outputs the root consumes. Outputs flow upward only.
🚀 Senior depthOutputs are the module's public API: they turn internal resource attributes into typed, documented values downstream code, other modules, and CI can rely on. "Display-only" or "console-only" answers confuse output blocks with terraform output reads.
🚩 Red flag"Only via remote state" — remote state wires stacks, not modules. Reaching across stacks for what an output already hands you is architecture by accident.
Q2 🔥Pin a registry module to 5.x. Exact block — and the risk if version is missing?
✅ Safe (junior→mid)source + version = "5.1.0" (or ~> 5.0). Source says WHERE, version says WHICH. Missing version floats — a future major can break runs that changed nothing.
🚀 Senior depthPinning without a source is a wish; sourcing without a pin is a gamble. Local paths take no version key (no registry to resolve); git URLs pin commits, not registry versions. For a bug-fix bump, pin the patched minor explicitly — review majors by hand.
🚩 Red flag"The registry pins automatically" — it doesn't. That sentence has caused more surprise majors than any other in this ecosystem.
Q3Which module sources are valid?
✅ Safe (junior→mid)Local paths, public/private registry, git URLs, HTTP/S3 archives — not just the public registry, not Docker Hub. Installed copies land in .terraform/modules after init.
🚀 Senior depthInit collision errors come from .terraform/modules, never the registry — two copies of one source collide locally; the registry is remote and read-only. New module + weird behavior → "did you init?" — apply only runs installed code.
🚩 Red flag"Only the public registry" — rules out every enterprise pattern (private registry, mono-repo local paths) in one breath.
Q4Should child modules declare provider blocks?
✅ Safe (junior→mid)Avoid it — inherit from the root. Provider config flows DOWN, never as a module input; required providers declare the dependency, the root supplies the configuration.
🚀 Senior depthHardcoded providers in children fork credentials, regions, and aliases per module — multi-region and multi-account compositions die there. Pass aliased providers explicitly only when a child must straddle configurations.
🚩 Red flag"Required in every child" — multiplies auth surfaces and guarantees the modules can't be reused across accounts.
Q5Walk me through the 4-stage modules evolution (3 S3 log buckets).
✅ Safe (junior→mid)Stage 1: 3 raw blocks, no vars (38 lines) → Stage 2: variables, still no loop (27) → Stage 3: vars + for_each (15) → Stage 4: vars + for_each on the module call (12 + 9-line reusable module).
🚀 Senior depthEach stage removes one axis of repetition: values → variables, copies → loop, pattern → module. Stage 4's module is copy-pasteable to any project — that portability, not line count, is the payoff. Data varies, logic stays single: add a map entry, get a bucket.
🚩 Red flag"Jump straight to modules" — modules generalize a pattern you haven't found yet; premature modules ossify three slightly-different buckets into an API nobody wants.
Q6Public vs private registry — when does the private one earn its keep?
✅ Safe (junior→mid)Access scope: the private registry hosts your org's blessed, versioned modules — the approved VPC, the compliant bucket — so teams consume gold instead of reinventing it.
🚀 Senior depthPrivate registry + version pins + Sentinel policy is the governance triangle: blessed code, locked versions, enforced rules. It changes nothing about init mechanics — same install, same .terraform/modules cache — it changes which code teams are allowed to reach for.
🚩 Red flag"Private is faster / skips init" — invents mechanics. The difference is scope and trust, not speed.

ZONE 7 · LIFECYCLE & GUARDS

Gates, Locks & Safe Surgery

🛡 6 Q · FIVE-GATE PIPELINE
📋 The five gatesfmt -check → init → validate → apply → plan (idempotent, no drift). Style, wiring, syntax, execution, proof. Name all five and the interviewer knows you've shipped, not just studied.
Q1 🔥CI must fail on unformatted HCL without rewriting. Command — and validate's job?
✅ Safe (junior→mid)terraform fmt -check — exit 1 on any unformatted file, zero writes. validate checks syntax + consistency with zero cloud contact: no credentials, no network.
🚀 Senior depthGate = -check (rewrites belong on laptops); format-on-save + CI -check covers prevention and enforcement. validate parses, resolves references, type-checks — anything needing AWS (refresh, diffs, costs) is outside its universe. -recursive covers subfolders; -diff previews.
🚩 Red flag"Bare fmt in CI" — gates must not mutate. A gate that rewrites is a race with the checkout it runs on.
Q2Second apply starts while the first holds the lock. What happens?
✅ Safe (junior→mid)It fails with a lock error naming the holder and lock ID — no parallel writes, no merges. Locks are protective, not punitive.
🚀 Senior depthOne lock table per env buys parallel applies across envs at the cost of more tables to guard; delete the table and applies run unlocked — last writer wins, silently. Lock fights mean a second writer: coordinate, don't force.
🚩 Red flag"Re-run with -auto-approve until it passes" — retries collide again without coordination, and -auto-approve near a lock fight is how two writers become zero states.
Q3 🔥Lock held by a dead CI runner. Exact recovery?
✅ Safe (junior→mid)Confirm death, then force-unlock by ID, then prove health. Verify no live process holds it first — stale crash, then release.
🚀 Senior depthForce under a live holder corrupts state for both runners — the cardinal sin. Deleting the DynamoDB row destroys locking for everyone; restoring backups fixes state, and the lock isn't state. Sequence it: prove dead → unlock by ID → plan clean before any apply.
🚩 Red flag"Delete the lock row by hand" or "destroy and recreate the bucket" — surgery for a splinter, with blast radius across every team sharing the backend.
Q4Why plan -out=tfplan + apply tfplan instead of bare apply?
✅ Safe (junior→mid)apply tfplan executes EXACTLY the saved plan — reviewed == executed, no drift between review and run. Bare apply re-plans interactively. Skipping plan risks approving a diff nobody read.
🚀 Senior depthThe saved plan is the deploy artifact CI gates on: show -json tfplan | jq .output_changes tells the pipeline what outputs will change before anything moves. -destroy plans the reverse; -refresh-only previews drift with zero writes.
🚩 Red flag"Bare apply in prod, I read fast" — prod applies run reviewed files behind approval gates. Confidence is not a control.
Q5Drift: console edit vs code. Detect, reconcile, modern refresh?
✅ Safe (junior→mid)A hand-edited tag surfaces as a ~ change — refresh imports REAL into the diff, then apply re-asserts code as truth. Bare refresh is legacy; prefer plan -refresh-only.
🚀 Senior depthDrift trilogy: console cause, plan detection, apply cure. Refresh-only writes lock/states accordingly (know your version's semantics); ignoring drift never self-heals and deleting .terraform touches binaries, not reality. apply -refresh-only commits the reconciliation when the console was right.
🚩 Red flag"Disable refresh" or "fmt -recursive fixes drift" — one blinds the detector, the other styles the code while prod burns.
Q6Rename web→app with zero rebuild; retire legacy without deleting it. Commands?
✅ Safe (junior→mid)state mv aws_instance.web aws_instance.app — new address, same cloud object, empty plan. state rm stops managing (instance keeps running); destroy deletes the object. Taint schedules DESTRUCTION — the opposite of a rename.
🚀 Senior depthBindings vs resources: mv renames the binding, rm drops it, import creates one — apply manages resources, never bindings. Prefer -replace over legacy taint for sick instances (snapshot stateful data first), state replace-provider after a fork, and snapshot with state pull before any surgery. Never hand-edit the JSON.
🚩 Red flag"Edit state JSON in an editor" or "taint and apply to rename" — one corrupts the ledger, the other destroys the thing you swore to keep.

ZONE 8 · MULTI-ENV & SCALE

Workspaces, TF_VAR & the ALB Stack

🌍 6 Q · ONE CODEBASE, THREE ENVS
📋 The mental modelWorkspaces isolate state, not code — one configuration, N state files under terraform.tfstate.d/<name>/. Per-env differences ride variables and terraform.workspace lookups, never copied folders.
Q1 🔥workspace show vs list — and which workspace can't be deleted?
✅ Safe (junior→mid)show prints only the active name ("where am I"); list prints all names. default is implicit and permanent — it survives every delete attempt.
🚀 Senior depthDeleting default would strand unscoped state, so migrate away from it instead. A brand-new workspace starts with empty state — first plan wants to create everything, which is exactly the surprise that bites during demos.
🚩 Red flag"Workspaces isolate code / providers / regions" — they isolate state. Regions live in provider blocks, code is shared; that's the entire point.
Q2What is terraform.workspace in code, and what's the idiom?
✅ Safe (junior→mid)A read-only string of the active name — the key into per-env maps: locals { env = terraform.workspace }, then lookup sizes, CIDRs, tags. Derive, don't repeat.
🚀 Senior depthSingle source per env: one map keyed by workspace beats conditionals scattered across resources. It never lists, versions, or addresses anything — backends come from blocks, resources from state, versions from the lock file.
🚩 Red flag"Use it for backend config" — backend blocks can't use var.* or workspace expressions; backend args come from -backend-config files.
Q3 🔥Defaults, TF_VAR, terraform.tfvars, -var all set region. Winner — and the TF_VAR map gotcha?
✅ Safe (junior→mid)-var wins. Ladder top-down: CLI flags → files (incl. *.auto.tfvars overlays) → TF_VAR_* env → defaults. Value surprise? Strip layers top-down; the stray flag is the prime suspect.
🚀 Senior depthTF_VAR maps need single-quoted HCL (shell-safe object syntax — bare braces split, double quotes interpolate). A variable with no default and nothing provided prompts — which hangs CI; always feed it via -var/env/file.
🚩 Red flag"Env vars beat files" — inverted ladder. Misordering the ladder means debugging values in exactly the wrong direction.
Q4tfvars discipline: what gets committed, what never does?
✅ Safe (junior→mid)Commit *.tfvars.example; ignore real *.tfvars, .terraform/, local state + backup. *.auto.tfvars loads automatically vs explicit -var-file — know which magic is active.
🚀 Senior depthterraform.tfvars committed with secrets is the incident: rotate, purge history, move values to env/Vault — the repo is never the answer. Rule of thumb: regenerable via init, or holds secrets → not in git.
🚩 Red flag"Commit .terraform/ so teammates skip init" — megabytes of re-fetchable binaries for zero reproducibility gain; the lock file already guarantees identical bits.
Q5 🔥Describe the ALB stack end to end (the project you actually applied).
✅ Safe (junior→mid)Public ALB (frontend EC2, public subnets) + internal ALB (backend EC2, private subnets): 2 target groups with HTTP health checks, 2 listeners, 4 attachments, 4 security groups, VPC plumbing — hashicorp/aws ~> 5.0, driven per-env via workspaces.
🚀 Senior depthVerified receipts: dev VPC vpc-5e7eebfd (10.30.0.0/16), 6 added after EC2-stub cleanup; staging vpc-82c9f766 and prod vpc-64c1ca93, 22 added fresh. Dev outputs carried both ALB DNS names (*.elb.localhost.floci.io), both TG ARNs, zone ID, VPC id — per-workspace state files ~52–69 KB, idempotent re-plan: "No changes".
🚩 Red flagReciting resources with no numbers, no workspace story, no idempotence proof — reads as a diagram memorized, not a stack shipped.
Q6How do backends scale across envs without var.*?
✅ Safe (junior→mid)Backend blocks take no variables — feed args via init -backend-config="env/dev.hcl" or per-env blocks. Each workspace keeps its own state file, so one codebase ships dev/staging/prod.
🚀 Senior depthSwitching Floci→real AWS later = repoint the endpoint variable + real credentials; the Terraform code doesn't change. Verification ritual per workspace: run-alb.sh (plan+apply+checks) → verify-alb.sh (health+endpoints) → terraform output → re-plan for the idempotence proof.
🚩 Red flag"One shared state file with env prefixes" — parallel applies across envs sharing one state is the lock-fight you scheduled yourself.

ZONE 9 · CLOUD & GOVERNANCE

TFC, Sentinel & Secrets

☁ 6 Q · REVIEWED == EXECUTED
📋 The governance triangleBlessed code (private registry) + locked versions (pins) + enforced rules (Sentinel) + secret-free repos (env/Vault). Miss one side and the other three can't save you.
Q1TFC vs TFE — and what does a TFC workspace bind?
✅ Safe (junior→mid)TFC = SaaS hosted by HashiCorp; TFE = self-hosted in your boundary. A TFC workspace binds config + variables + state + run history — run history lives there, not on laptops.
🚀 Senior depthHeavy teams outgrow the free tier into paid runners/agents: remote operations run on your infra via agents, so plans execute identically for every engineer. "Just the CLI binary" or "display only" answers miss that the workspace is the collaboration unit.
🚩 Red flag"TFE is older Terraform" — confuses a deployment model with a version. Says you've never had to place a compliance boundary.
Q2 🔥PR opened → plan posted back → merge → apply. Name it and defend it.
✅ Safe (junior→mid)VCS-driven runs. Remote runs fire on VCS events; the speculative plan lands as a PR comment with zero state risk; merge gates the apply.
🚀 Senior depthSpeculative plans analyze the plan remotely — same engine feeds cost estimates on the PR. Golden rule: infra change without a PR is an incident report waiting for a timestamp. Console runs, local-exec, and state mv are unrelated machinery.
🚩 Red flag"We apply from laptops, it's faster" — speed that skips review, audit trail, and identical execution is the thing governance exists to kill.
Q3 🔥Sentinel: mandatory vs soft-mandatory vs advisory?
✅ Safe (junior→mid)Missing cost tags, no override → mandatory: never passes. Soft-mandatory: passes only with an override by someone holding the right; advisory: warns, never blocks.
🚀 Senior depthThe axis is override possibility — permitted vs never — not speed or language. Design rules so the common path flows (advisory for new standards, soft-mandatory during rollout, mandatory once the org can comply), or engineers route around the policy system entirely.
🚩 Red flag"Everything mandatory" — a policy set nobody can satisfy is a policy set everybody bypasses. Governance that blocks work gets uninstalled.
Q4Where do secrets actually live — state, tokens, CI creds?
✅ Safe (junior→mid)State holds secrets in plaintext — restrict the bucket + IAM, use Vault/SSM. login tokens live in credentials.tfrc.json (home dir, never the repo). CI creds flow via env vars / OIDC — keys leave the repo after one scare.
🚀 Senior depthThe backend checklist is versioning + encryption + locking together — each alone is necessary and insufficient. Hardcoded keys are the incident, tfstate is the leak surface, Vault is the enterprise answer; the repo is never any answer.
🚩 Red flag"State encrypts secrets by default" / "outputs are always encrypted" — both fictions. Believing either is how plaintext lands in git and logs.
Q5Why is output -raw db_password in CI logs a violation? The ephemeral escape hatch?
✅ Safe (junior→mid)sensitive masks display, not storage — piping -raw to logs leaks the value anyway. Mask the output, pipe it to a store. ephemeral = true means never stored in state: same-apply read only.
🚀 Senior depthTwo different guarantees people merge: display masking (console/logs) vs state exclusion (ephemeral). Secrets need the second; the first is cosmetics. Audit for -raw and -json | jq in pipelines — that is where masked values go to become headlines.
🚩 Red flag"sensitive = true encrypts it" — the sensitive-display myth. It masks; the plaintext sits in state either way.
Q6Cost estimate on the PR and private registry — where do they come from?
✅ Safe (junior→mid)Cost estimates come from remote runs analyzing the plan — not local fmt, not the console. The private registry gives the org a blessed, versioned module/provider list.
🚀 Senior depthEstimate-before-merge turns the PR into a budget review: tag policies + cost deltas visible before a dollar is committed. Pair it with mandatory tag Sentinel rules and untagged spend can't even reach the estimator.
🚩 Red flag"The bill comes from terraform show" — show reads state/plans; it prices nothing. Confusing inspection with estimation.
